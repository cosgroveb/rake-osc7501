# Contributing

Follow the [code of conduct](CODE_OF_CONDUCT.md). Report vulnerabilities through
the private channel in [SECURITY.md](SECURITY.md).

AI-assisted contributions are welcome. Before requesting review, understand
the changes, run relevant checks, and verify claims in code, documentation,
and reports. State what you tested and what remains uncertain. Be prepared to
explain your choices and address feedback. When using an agent to help answer
a reviewer, check the answer and send only what is relevant.

Use MRI Ruby 3.4 or newer for development tooling. Install actionlint 1.7.12 on your PATH, then run all checks:

```sh
bundle install
bundle exec rake
```

The default task runs RuboCop with rubocop-rspec, bundler-audit, actionlint,
inline RBS checks, specs, installed-gem smoke tests and RDoc. Run `bundle exec rake lint`, `audit`, `workflows`, `types`,
or `spec` for individual checks. RuboCop applies default style rules to release tooling and build configuration,
and correctness cops to existing runtime code, fixtures and smoke tests.
Scoped exclusions preserve Ruby 2.1 support and exception propagation. Do not add a TODO baseline. Dependency auditing checks the
lockfile generated by `bundle install`. Keep that lockfile out of commits.

`rake types` uses Steep to check runtime and tooling implementations in `lib/`
and `script/` against generated inline signatures. Specs and build configuration
receive annotation and signature validation only. Keep project types inline.
`sig/dependencies.rbs` fills gaps in dependency signatures, and generated files
stay in ignored `tmp/`.

Specs run in random order and report their seed. Reproduce an ordering failure
with `bundle exec rspec --seed <seed>` and narrow it with
`bundle exec rspec --seed <seed> --bisect`. Generated subprocess fixtures keep a
defined order because their interrupt and fail-fast cases depend on sequence.

Keep runtime dependencies limited to `rake`. Cover task lifecycle behavior with real Rake subprocesses.
The normal development bundle includes `rspec-osc7501`, so `bundle exec rake spec`
also checks paired reporting. Set `RSPEC_OSC7501_PATH` before `bundle install` to
use a local companion checkout.

Build the gem and documentation:

```sh
bundle exec rake package
bundle exec rake smoke
bundle exec rake rdoc
```

The package is `pkg/rake-osc7501-<version>.gem`. Open `tmp/rdoc/index.html` to check
rendered documentation. `rake package` generates runtime RBS from `lib/` into
`pkg/rake-osc7501-<version>/sig/` and includes it in the gem for type tools to
discover by gem name. Keep generated files out of commits.
The smoke task builds and installs the gem in a temporary directory, then checks
passing and failing tasks without loading the checkout's library.
The `pure-rake` CI job runs this check with only Rake and the built gem installed
in the isolated directory, and rejects any installed RSpec gems.

## Runtime compatibility

The gem requires MRI Ruby 2.1 or newer and Rake 12.3.3 or newer.
Use `Gemfile.compat` to test the runtime without modern lint, release or RDoc
dependencies. On Ruby 2.1, install Bundler 1.17.3 first. Set the RSpec version
before resolving dependencies:

```sh
export BUNDLE_GEMFILE=Gemfile.compat
export RSPEC_MINOR=3.6
export RSPEC_CORE_VERSION=3.6.0
bundle install
bundle exec rspec --options '' spec/rake
bundle exec gem build rake-osc7501.gemspec
bundle exec ruby script/smoke.rb rake-osc7501-*.gem
```

Remove `Gemfile.compat.lock` before changing RSpec versions. Keep it out of commits.
The compatibility bundle pins diff-lcs 1.3 so test dependencies install on Ruby 2.1.
These bare `gem build` checks omit generated signatures and need no type tooling.
Use the modern development bundle and `rake package` for distribution builds.
CI checks the oldest Ruby against both RSpec endpoints, the oldest RSpec on modern
Ruby, and the Debian Bullseye and Bookworm version families. These jobs run the
runtime suite and installed-gem smoke checks. Modern jobs also test release
automation, lint and documentation.
CI also checks RSpec 4.0.0.beta1 on Ruby 4.0.

Compatibility checks use available patch releases within each Ruby series.
Supporting an older runtime does not extend its upstream security maintenance.
Unset `BUNDLE_GEMFILE`, `RSPEC_MINOR`, `RSPEC_CORE_VERSION` and `RSPEC_VERSION`
before returning to the modern development bundle.

Update usage or behavior documentation for user-visible changes. Write commit
subjects that describe the change, because release notes use those subjects.
Do not maintain `Unreleased` entries by hand. Preserve the Apache-2.0 license text.

## Release

Release the reviewed commits on remote `main`. Replace `NEW_VERSION` with a
stable version greater than the current release (use `0.1.0` for the first release):

```sh
gh workflow run release.yml --ref main -f version=NEW_VERSION
```

The workflow captures `main`, updates `VERSION`, and generates CHANGELOG bullets
from non-merge commit subjects since the previous release tag. It preserves
older changelog sections and uses the same notes for the GitHub Release.
Versions must use `major.minor.patch` without a `v` prefix or prerelease suffix.
After the first release, a new version must exceed the current version and
include new commits. The first release accepts the source version and derives
notes from initial history when no release tags or dated changelog exist.

The full CI matrix tests the prepared release commit before the workflow pushes
it and its tag together. If `main` advances during testing, the workflow stops.
After the push, it publishes to RubyGems, then creates the GitHub Release. No
intermediate approval is required.

If a release fails, inspect its logs and rerun the same version. If its tag
already exists, the workflow tests and resumes that tagged release instead of
releasing newer commits on `main`.

### One-time publishing setup

Before the first publication, configure a RubyGems pending Trusted Publisher with owner `cosgroveb`,
repository `rake-osc7501`, and workflow `release.yml`. Leave the environment
blank. The workflow uses short-lived OIDC credentials, with no RubyGems token
stored in GitHub secrets. Repository Actions permissions must permit the
workflow's `contents: write` and `id-token: write` requests.

Store a dedicated write-enabled repository deploy key as the Actions secret
`RELEASE_DEPLOY_KEY`. Only the publish job uses it to push the tested commit
and tag. Require PRs and CI checks in a separate ruleset with deploy-key bypass,
and keep deletion and force-push protection in a ruleset without bypasses.
GitHub applies this bypass to all repository deploy keys, so additional write
deploy keys would receive the same access. GitHub API calls still use the
workflow token, and RubyGems still uses OIDC.
